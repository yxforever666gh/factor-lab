[Sat 2026-04-04 03:21 GMT+8] Durable summary of research runtime hardening work and current project state.

Context / user intent:
- User explicitly wants the project to remain an autonomous research agent focused on factor quality discovery/validation, not a cron-like fake autonomy, and not a system that needs manual babysitting after every failure.
- User was concerned that bug fixes might have damaged core research goals or autonomy. Important constraint going forward: runtime/stability fixes must not silently alter research logic/goals without explicit approval.

What was implemented during this session:
1) Runtime stability / memory hardening
- batch default concurrency reduced to 1 via env-driven worker cap.
- research daemon now supports self-recycle after a task budget and on daemon RSS threshold.
- heavy task execution moved out of daemon process into short-lived worker subprocesses for workflow / batch / generated_batch.
- report refresh was throttled (default cooldown window) to reduce repeated heavy rebuilds.
- parent process now enforces worker wall-clock timeout and worker RSS limit; if a worker exceeds limits it is killed.
- if worker exits abnormally but outputs are already complete, task is recovered as finished instead of retried.

2) Queue/orchestrator safety
- generated_batch preflight validation added.
- deterministic vs transient failure classification added.
- deterministic failures no longer blindly retry; quarantine path added.
- family-scoped blocking/skipping added so unhealthy generated_batch tasks do not automatically block diagnostics and other healthy task families.
- blocked/repeated-RSS generated_batch tasks can now be auto-quarantined out of the active queue so planner autonomy can continue.

3) Opportunity budget guard
- opportunity -> task mapping now guards budget-risky cases upstream.
- specifically, probe + cheap_screen + empty target_candidates is downgraded away from heavy generated_batch execution (to a lighter diagnostic path) instead of entering the heavy path directly.
- normal probe tasks with explicit target_candidates still map to generated_batch; exploration was not globally disabled.

Observed root causes / important lessons:
- The original severe memory issue was architectural: long-lived research daemon was carrying repeated heavy pandas/numpy/SQLite workloads and could accumulate RSS over many loops.
- After subprocessization, a second issue appeared: heavy worker subprocesses could still blow up memory, and if interrupted after outputs were already written, the orchestrator previously retried them, creating the appearance of endless memory growth via repeated new Python3 workers.
- Another autonomy bug appeared: blocked bad pending tasks could remain in queue long enough to prevent planner injection, causing "runs one, then stops" behavior that violated user intent. This needed explicit auto-quarantine / ignore-blocked-for-injection logic.
- Key principle learned: protect runtime without breaking autonomy. Safety/guardrails must eject bad branches from the active queue and allow healthy research continuation automatically.

  - systemd/factor-lab-research-daemon.service

Performance investigation and durable findings:
- User correctly noted prior throughput/concurrency tweaks had almost no real effect on CPU usage (still ~15-30%).
- Root cause discovered: the research daemon/orchestrator was effectively serial on heavy tasks. `max_tasks` previously meant "process up to N sequentially" rather than true concurrent heavy-task execution.
- This was corrected so the orchestrator can process a claimed batch concurrently instead of waiting for each heavy task one by one.
- More importantly, profiling showed the main workflow bottleneck was `factor_eval`, which consumed ~80%+ of workflow wall-clock time on representative runs.
- Typical pre-optimization workflow timings were roughly:
  - rolling_30d_back: total ~58.8s, factor_eval ~49.9s
  - rolling_60d_back: total ~56.5s, factor_eval ~46.9s
- A naive attempt to parallelize `factor_eval` with threads made things worse:
  - 1 worker benchmark: wall ~58.82s, factor_eval ~49.92s
  - 4 workers benchmark: wall ~77.41s, factor_eval ~68.77s
- Durable lesson: naive thread parallelism on the current pandas/Python path is a negative optimization due to Python-level loops / contention / copy overhead.

Effective performance optimization that should be remembered:
- The correct direction was algorithmic optimization of `evaluate_factor` and reducing repeated split/rolling filtering overhead, not naive multithreading.
- After optimizing `evaluate_factor` and reducing repeated set/isin/copy work for split/rolling paths, a representative workflow improved dramatically:
  - from ~58.81s total / ~49.92s factor_eval
  - to ~32.54s total / ~21.41s factor_eval
  - and then further to ~27.33s total / ~17.90s factor_eval
- Durable conclusion: algorithm-level optimization of the evaluation path delivered roughly >50% total workflow speedup and >60% factor_eval reduction on the representative case.
- This is a major validated direction for future speed work; optimize the hot numeric path first, then reconsider concurrency.
